# CodeVerse Governance

CodeVerse uses lightweight, maintainer-led governance. The goal is to make decisions in public without pretending a young project needs a large committee.

## Roles

### Users

People who try CodeVerse, report problems, ask questions, or share feedback. Clear reproduction steps and honest usability feedback are valuable contributions.

### Contributors

People whose documentation, design, code, tests, reviews, or community work has been accepted into the project.

### Recurring contributors

Contributors who repeatedly demonstrate sound judgment in a project area. They may be asked to triage issues, review pull requests, or help shape milestones in that area.

### Maintainer

The maintainer is responsible for releases, security response, repository access, architecture boundaries, and final merge decisions. Ayush Kumar is the current primary maintainer.

## How decisions are made

- Small fixes are decided through issue and pull-request review.
- Changes to public contracts, architecture, security boundaries, or project direction begin in GitHub Discussions.
- Decisions favor the smallest solution that is understandable, testable, and reversible.
- The maintainer makes the final call when consensus is unclear or user safety is involved, and records the reasoning publicly when practical.

## Path to maintainership

Repository access is earned through sustained work rather than requested through a single contribution. Signals include:

- several high-quality contributions over time;
- constructive reviews and issue triage;
- reliable follow-through on regressions;
- respect for security and compatibility boundaries;
- patient support for newer contributors.

New maintainers receive the least privilege needed for their responsibility and may step back at any time.

## Conflicts of interest

Anyone making a decision should disclose a relevant employer, client, financial, or personal interest. A different maintainer or a clearly documented public rationale should be used when a conflict could reasonably affect trust.

## Changes to this document

Governance changes should be proposed in a public discussion and merged through a pull request. The structure should grow only when real community needs justify it.
