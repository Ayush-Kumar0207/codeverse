# CodeVerse demo script

Target length: 75–90 seconds. Record the real product in one continuous browser session, then trim pauses. Do not use simulated activity or replace product output with motion graphics.

## Storyboard

### 0–8 seconds — the problem

**Screen:** Landing page, then the live demo call to action.

**Voiceover:** “Most browser IDEs help you write code. CodeVerse also keeps the context needed to understand, review, and safely undo a change.”

### 8–25 seconds — build together

**Screen:** Open the same project in two browser windows. Type a short change in one window and show it appear in the other with collaborator presence visible.

**Voiceover:** “The editor uses Yjs and Socket.IO for live collaboration, with Redis-backed room and permission state so sessions can move across server instances.”

### 25–40 seconds — run and understand

**Screen:** Run the project, show output, then open one algorithm trace or focused explanation.

**Voiceover:** “You can run multi-language workspaces, inspect the result, and use focused explanations without leaving the workspace.”

### 40–58 seconds — review the change

**Screen:** Open Assistant and request a review. Show the returned findings, then switch to Team briefly.

**Voiceover:** “The Assistant reviews the active change in context. Collaboration and review stay connected to the project instead of becoming separate chat history.”

### 58–73 seconds — prove it

**Screen:** Open Proof Center. Show coverage, one evidence item, and the replay or recovery path.

**Voiceover:** “EvidenceOS links the change to execution, review, rationale, and recovery evidence, so a reviewer can inspect what happened instead of trusting a green badge alone.”

### 73–88 seconds — invite participation

**Screen:** GitHub README Start here table, one good first issue, and the Discussions page.

**Voiceover:** “CodeVerse is MIT licensed and feature-frozen while I focus on reliability and contributor experience. Try the demo, tell me where it becomes confusing, or pick up a focused issue on GitHub.”

## Recording notes

- Use a real, small project that fits on screen; avoid the word “demo” in the project title.
- Keep the browser at 100% zoom and hide unrelated tabs, bookmarks, notifications, and personal account details.
- Warm the free-tier backend immediately before recording, but disclose cold starts in the launch text.
- Use one calm cursor path. Pause for half a second after each navigation so viewers can follow it.
- Add captions from the final voice track and manually correct product names and technical terms.
- End on the repository URL and the words “Try it. Break it. Help improve it.”
